# E4 Cost-Study Protocol — LLM Metadata Enrichment: Time & Effort (DSS RQ4)

**Purpose:** measure what LLM metadata enrichment *costs* in cataloger time
and editing effort, versus cataloging from scratch — the cost side of the DSS
decision model (gain per cataloger-hour). Companion to
`cataloger_panel_materials.md` (Activity 1 = gold validation) and
`plan/extended_journal_paper.md` (E4 / RQ4).

**Date:** 2026-09-05

---

## 1. Design summary

| Element | Value |
|---|---|
| Participants | 2–3 professional catalogers (or advanced cataloging students supervised) |
| Records per cataloger | **80** — 40 manual (M) + 40 verify (V), disjoint within cataloger |
| Record pool | 204 gold-bearing (tier-1) LIBRA-CAT records (gold LCSH + DDC + clean LLM prediction) |
| Input shown | **title, author, year only** — identical to the LLM cataloger's input, so M vs V is a fair effort comparison |
| Condition order | Counterbalanced across catalogers (cataloger 1 starts M, 2 starts V, 3 starts M, …) |
| Measures | time per record (instrumented), edits per record (V), final quality vs gold (multi-level rubric) |
| Instruments | per-cataloger HTML tool with per-record timer + CSV workbook fallback (generated) |

---

## 2. Why title/author/year only

LIBRA-CAT's LLM cataloging ran in the *retrospective-conversion* setting:
the model saw only a minimal record (title, author, year) and proposed LCSH +
DDC. If manual catalogers saw the full book, the comparison would measure two
different tasks. Giving both conditions the same sparse input keeps the
comparison clean: any time difference is attributable to the draft, not to
different information.

> Limitation to state in the paper: manual catalogers working from sparse
> records is itself a specific setting; full-text-conditioned cataloging
> (journal plan E3) is the companion question, run separately.

## 4. What each cataloger does

1. Open their instrument HTML in a browser (or the workbook CSV).
2. For each of 80 records:
   - **M (manual):** assign LCSH subject headings (one per line) and a DDC
     number from title/author/year only.
   - **V (verify):** edit the machine draft into final headings + DDC — keep,
     change, add, or delete as they judge correct. They are told drafts are
     AI-generated, not which model.
3. The timer runs while an item is on screen; pauses between items are free.
4. Download `cataloger_<X>_results.csv` and return it.

Time estimate: ~2.2 min/item → **~3 h** per cataloger (split across sessions
is fine; progress autosaves in the browser).

## 5. Analysis (score_cost_study.py)

```bash
# after results CSVs are returned into phase1/data/panel/e4/:
python3 phase1/scripts/score_cost_study.py
```

Reports:

1. **Time:** mean seconds/record M vs V per cataloger and pooled; %
   time saving. Records are disjoint between M and V, so the comparison is
   independent — report per-cataloger means and variance, not a paired test
   by record. A paired test across catalogers (mean_M − mean_V per cataloger,
   n = number of catalogers) is the honest significance statement.
2. **Edits (V):** share of records the cataloger changed from the draft, mean
   changed headings — a proxy for how much the draft *helped* vs how much it
   *misled*.
3. **Quality parity:** final headings in M vs V scored against gold with the
   LIBRA-CAT rubric (exact / semantic / acceptable coverage of gold
   headings). The key claim: V is faster at *no quality cost* — or quantify
   the trade if there is one.
4. **Draft as floor (V):** draft score vs cataloger-final score — does
   editing improve on the draft? This separates "the draft was good and the
   cataloger kept it" from "the cataloger fixed a bad draft" (the latter
   being hidden cost).

Quality scoring uses the same normalization + MiniLM semantic matcher as
`score_libra_cat.py`; scores should be read against the **inter-cataloger
agreement ceiling** from Activity 1 (as everywhere in LIBRA-CAT).

## 6. Pre-registration notes (what to fix before collecting)

- **Primary outcome:** time per record (M vs V), per cataloger.
- **Secondary:** any-level heading coverage of gold (M vs V); edit rate (V).
- **Analysis:** per-cataloger means; report all catalogers individually, never
  only the pool; the small-n (2–3 catalogers) cost estimate should be framed
  as a pilot cost function, with the model's sensitivity explored in the DSS
  decision analysis rather than over-claimed.
- **Exclusions:** records with a generation failure (none in the 204 pool);
  sessions interrupted >30 min (flag and report).
- **Counterbalancing check:** confirm each cataloger's condition order matches
  the file (cataloger 1 M-first, 2 V-first, …) before analysis.

---

## 7. What feeds the DSS paper

- The **cost function** (minutes/record, M vs V) × the **gain function**
  (E1 sparsity sweep) = discovery gain per cataloger-hour → the decision
  curve (RQ5) and break-even analysis.
- The **edit-rate** and **draft-as-floor** results tell a manager how much
  trust to place in raw drafts vs verified output.
- Activity 1's agreement ceiling calibrates the quality numbers; both panel
  activities are cited together as "validated against professional judgment."

## 8. Sequencing

1. Recruit catalogers (`phase1/outreach_catalogers.md`); send each their
   `_instrument.html` + `_instructions.md`.
2. Run Activity 1 (gold validation, ~60 records) before or alongside.
3. Collect E4 results; run `score_cost_study.py`.
4. Feed cost + gain into the DSS decision analysis.
